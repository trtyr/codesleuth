# 微观 · 报告生成（report）

> 置信度 medium · 7 条发现 · 242879 tokens

报告生成链路（submit_report → build_report → Report/validate → render_human → RunOutcome/CLI 持久化，及 prose 降级路径）整体结构清晰、防御注释密集，但存在三处真实正确性缺陷：①证据门禁「必须真实读过文件」的承诺与实现不符——EvidenceStore.observe 会把任何工具输出（find_files/grep 列表、错误信息）中出现的类路径 token 记为「已观察」，模型可引用从未 read 过的文件并通过 uncited 校验；②render_human 把「findings 为空」硬编码等价为降级报告，而 build_report 明确允许零 findings + dead_ends 的合法非降级报告，被误渲染为「降级报告」；③降级路径不校验 answer 为空——strip_task_echo 可把纯任务回显剥成空串，产出 answer 为空的降级报告（submit 路径有此校验，降级路径漏了，典型复制粘贴改漏）。另有 validate 误用 INDEX_BUILD_FAILED 错误码、info_keys 全量 sha256 指纹疑似架空零增量熔断两个次级问题。bug 密度最高文件：src/harness.rs 与 src/report.rs。最值得先修：render_human 的 findings 为空分支应改为基于 self.degraded 判断。

1. P2 证据门禁承诺与实现不符：工具 schema 与描述声称「evidence 必须引用本会话真实读过的文件」（harness.rs:491），但 EvidenceStore.observe 对任意工具输出切词，凡含 / 或 . 的 token（find_files 列表、grep 命中行、错误信息中的路径）一律入库为「已观察」，build_report 的 cite_seq 校验（harness.rs:567-579）据此放行——模型可以引用从未 read 过的文件并通过 uncited 检查，报告以非降级 + audit_seq 锚点的「可信」形态输出。上游防线不成立：这是唯一的引用校验点，无二次核验。（src/harness.rs:491-506、src/evidence.rs:44-51、src/harness.rs:567-579）
2. P2 渲染误标降级：render_human 在 findings 为空时硬编码输出「（无结构化发现——降级报告）」（report.rs:83-84），但 build_report 明确允许零 findings + 非空 dead_ends 的合法非降级报告通过（harness.rs:616 只在 dead_ends 也为空时打回）。触发条件：模型诚实空手并用 dead_ends 交代，提交成功且 degraded=false，渲染却声明是降级报告——与同函数 108-112 行基于 self.degraded 的正确标注自相矛盾（复制粘贴假设改漏）。上游防线不成立：该字符串直接进入 CLI 的 md/json 输出，无人再纠。（src/report.rs:83-84、src/harness.rs:616-628）
3. P2 降级路径漏掉空 answer 校验（提交路径有、降级路径无）：prose 降级分支 answer = strip_task_echo(task, &resp.text) 后直接构造 Report::degraded_prose 返回，全程不调用 validate；当弱模型最终 prose 恰为纯任务回显（该函数的靶场景）时，剥除后 answer 为空串，产出 answer="" 的报告并写盘/输出。而 submit 路径 build_report:601 显式拒绝空 answer，Report::validate:67 也定义了该校验——降级路径绕过了它。上游防线不成立：CLI 序列化直接落盘，无再校验。（src/harness.rs:212-242、src/harness.rs:601-603、src/report.rs:67-72）
4. P3 错误码误用：Report::validate 的两处报错（非法置信度、空 answer）均使用 INDEX_BUILD_FAILED 错误码，与语义（报告内容校验）完全不符，退出码/故障域分类会误导调用方判为索引构建故障。（src/report.rs:59-72）
5. 疑似 P3 零增量熔断被内容指纹架空：info_keys 除路径 token 外总是追加整段输出的 sha256 前 8 字节（evidence.rs:16-18），任何内容不同的工具输出都产生新 key → harness.rs:444 判为「有增益」→ no_progress 清零。后果：模型只要让每次调用参数略有差异（如 grep 模式微调，返回「0 命中」等不同文本），无进展熔断（MAX_NO_PROGRESS_STREAK=5）永不触发，可无限空转烧 token。疑似理由：注释表明「内容指纹=增量记账」或有设计意图；验证方法：回放一组参数各不相同但均无有效结果的调用序列，观察 no_progress 是否恒被清零。（src/evidence.rs:16-18、src/harness.rs:443-452）
6. 死代码：fence.rs resolve 中 `if candidate.is_absolute() ... else current_dir().join(...)` 的 else 分支不可达——root 经 dunce::canonicalize 必为绝对路径，root.join(rel) 恒为绝对路径（rel 为绝对串时 join 直接替换仍为绝对）。确定死（词汇可达性即可证明）。（src/fence.rs:30-42）
7. 已审干净面说明：submit_report 主路径的参数解析失败/未知工具/重复调用/非法 JSON 分支均计 no_progress 并回显（harness.rs:265-411），uncited 拒绝、零 findings 打回、裸 finding 拒绝三重门依次核对无逻辑反转；strip_task_echo 的循环有 rest==before 终止条件且边界字符防误剥（harness.rs:686-725）；audit record 锁内取号保证 seq 单调；recall 的 from/to 默认值（0/from）与 read_range 闭区间语义核对无越界；CLI 报告落盘（md/json/--out 三通道）与 OutputFormat 分发核对一致；tests/replay.rs 对工具序列与 schema 的契约断言与实现一致。（src/harness.rs:264-362、src/harness.rs:686-725、src/report.rs:59-74）
