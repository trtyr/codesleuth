# 微观 · read工具（read-tool）

> 置信度 high · 7 条发现 · 316330 tokens

read 工具链路（ReadTool.execute → Fence.resolve → fs::read → lossy 解码 → 分页/锚点输出 → Harness 增量记账/EvidenceStore 存证）总体实现干净：offset 边界、截断续读、空文件/二进制/非UTF-8 诚实声明均正确，测试覆盖到位。发现 2 个真实缺陷与若干 P3 偏差：(1) fence.rs starts_with_root 用 zip 前缀比较，当目标路径是围栏根的严格祖先（如 ".." 或 "../.."）时 zip 提前耗尽返回 true，resolve 会 Ok 返回围栏外目录而非 FENCE_DENIED——防线靠 read 的 is_file 兜底才未泄漏内容，但围栏契约被击穿；(2) EvidenceStore.observe 对所有工具输出做 path_like 切词入库，任何工具输出中被"提及"的路径（如 read 到的文件内容里写着 src/foo.rs）都能通过 submit_report 的 cite_seq 校验，证据契约"必须真实读过"可被未读文件引用满足。另有 offset/limit 非法值（负数/0/浮点/超上限）被静默归一为默认/边界值无任何告知、12-bit 锚点与"行内容一变锚点即失效"的文档承诺存在 1/4096 碰撞概率、工具执行失败分支不写 tool_result 审计记录等 P3。死代码维度基本干净（预留错误码有注释登记，非残余物）。

1. 【P2 · 围栏契约击穿】starts_with_root 用 p.components().zip(root.components()).all(...) 判前缀：当 p 是 root 的严格祖先（分量更少）时 zip 提前结束返回 true。Fence::resolve("..") 或 "../.." 经 normalize 折叠后得到围栏根的祖先目录，两层检查（词汇层 line 37 与 canonicalize 后 line 48）都放行，返回 Ok(围栏外目录) 而非 FENCE_DENIED。触发条件：模型传 path=".."；错误行为：resolve 成功返回围栏外路径；应有行为：FENCE_DENIED。上游防线为何不成立：read.rs:87-92 的 is_file 检查恰好把目录挡成 REPO_NOT_READABLE，才使本链路未实际泄漏文件内容——但 Fence 是跨工具共享的第二层安全边界（fence.rs:1 注释自述'越界一律拒绝'），其自身承诺已被违反，且 error message（'不是普通文件' vs '路径不存在'）泄露围栏外目录存在性。验证法：Fence::new(tempdir).resolve("..") 应返回 Err 而实际返回 Ok(父目录)。（src/fence.rs:75-88、src/fence.rs:59-71）
2. 【P2 · 证据契约可绕过】EvidenceStore::observe（evidence.rs:44-51）对每次工具成功输出做 path_like 切词入库，与 read 专用的 observe_exact（:35-37）共用同一 paths 表；build_report 的 cite_seq（harness.rs:567-579）对两者不区分。任何工具输出中被提及的路径——如 read 到的源码里写着 "src/foo.rs"、grep/find_files 列表里的路径——都会成为可引用证据，模型可对从未 read 过的文件提交 evidence(file:lines) 且通过校验。触发条件：模型在 findings.evidence 引用一个仅在其他工具输出文本中出现过的路径；错误行为：校验通过、audit_seq 指向无关 seq；应有行为：按 harness.rs:491 与拒绝语（'evidence 必须引用本会话真实读过的文件'，:606）应拒绝。上游防线为何不成立：uncited 检查（:604-609）只挡 paths 表外的路径，挡不住表内'提及未读'的路径。（src/evidence.rs:44-51、src/harness.rs:426-442、src/harness.rs:567-579）
3. 【P3 · 参数静默归一】read 的 offset 用 as_u64().unwrap_or(1).max(1)、limit 用 clamp(1,2000)：负数/0/浮点 offset 静默变为 1，limit=0 变 1、limit>2000 被静默截到 2000，无任何提示，与'诚实反馈'特性不对称。同模式复制到 harness recall 的 from/to（harness.rs:344-345，缺省 0）。触发条件：模型传 offset:0 或 limit:5000；错误行为：按 1/2000 执行且输出头不声明限幅；应有行为：至少在输出头声明实际生效值或返回 USER_INPUT。上游防线不成立：LLM 网关不做 schema 数值校验，工具层是最后防线。（src/tools/read.rs:75-84、src/harness.rs:344-346）
4. 【P3 · 锚点碰撞概率被文档夸大】line_hash 取 SHA-256 前 12 bit（4096 种值），注释称'行内容一变锚点即失效，防张冠李戴'（read.rs:25）——实际两行不同内容碰撞概率约 1/4096，单次 200 行窗口内存在碰撞概率约 0.6%+，锚点并不能保证区分。属文档/承诺与实现的偏差，非功能破坏。（src/tools/read.rs:25-29、src/tools/read.rs:135-135）
5. 【P3 · 工具失败无 tool_result 审计】harness 主循环成功路径写 tool_call（:414-417）+ tool_result（:429-432）两条审计，但 execute 失败分支（:468-479）只把错误消息推回 LLM，不落任何 tool_result/tool_error 审计行——审计账本里 tool_call 变成无结果的孤儿记录，recall 钻取该 seq 只见调用不见失败原因（失败原因只存在于 LLM 上下文）。（src/harness.rs:413-417、src/harness.rs:468-479）
6. 【已审为净】read.rs execute 主体（:66-146）：offset>total 边界、end=min(offset-1+limit,total)、skip/take 行号对齐、截断续读 offset=end+1、total==0/二进制/lossy 声明分支逐一心算代入（空文件、单行、offset==total、无尾换行、CRLF、全 FF 字节、恰好 8192 字节头）均正确；五特性与 description/parameters 三方一致；单测（:159-227）覆盖分页、二进制、lossy、空、越界、缺参。（src/tools/read.rs:66-146、src/tools/read.rs:97-98、src/tools/read.rs:120-144）
7. 【死代码维度·基本干净】链路内未发现确定死代码：errors.rs:50/56 的预留码（4012/4013/5099）有显式注释登记为预留非残余；ToolRegistry 全方法（register/get/schemas/is_empty）均有生产调用；read.rs 无注释代码块、无 TODO-FIXME、无调试残留。（src/errors.rs:50-56、src/tools/mod.rs:34-58）
