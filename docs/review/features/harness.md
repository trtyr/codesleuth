# 微观 · Harness主循环（harness）

> 置信度 medium · 11 条发现 · 907500 tokens

Harness 主循环链路（harness.rs run/build_report + audit/evidence/context/report/llm/tools/cli）整体结构清晰、多数历史坑已有回归测试与注释防护，但仍发现 5 个真实正确性缺陷（3×P1 + 2×P2 + 若干 P3）与 3 处死代码。最严重的三个：① read 工具调用只要发起（无论成败）就把模型传入的 path 写入证据库（observe_exact 在 execute 之前取参、结果 match 之外无条件入库），削弱 build_report 的「未读过文件不得引用」防线；② prose 降级路径不校验 answer 非空（submit 路径在 build_report:601 拒空，降级路径 Report::degraded_prose 不经 validate），模型返回 text=None 的无工具轮会产出空 answer 的 RunOutcome；③ contract_repaired 单预算被 submit 与 prose 两条通道共享，文档声称「补一轮修复引导」按通道，实际 prose 转向一次就烧光预算，随后首次 submit 违约直接 CS2005。死代码维度：CsError::retryable() 确定死（零生产调用），McpClient::list_tools 与 RecallEngine 的 tombstone/compact 簇为预留/疑似死。bug 密度最高文件：src/harness.rs。

1. 【P1·证据库污染】harness.rs:421-425 在调用 tool.execute 之前从 read 参数摘出 read_exact_path，随后在 execute 的 Ok 分支（437-442）无条件 observe_exact 入库。看似只记录成功读取，但注意该摘取对一切 name=="read" 的调用生效，且「成功」的判定只看 execute 返回 Ok——而 read.rs 的特性 5（read.rs:111-118）在空文件/offset 越界时返回 Ok 的提示文本（未读任何行），二进制文件也返回 Ok 拒倾倒文本（read.rs:98-103）；这些情况下模型并未观察到文件内容，路径却已入 EvidenceStore。错误行为：模型 cite 一个只读过「二进制文件，不倾倒内容」或 offset 越界提示的文件，cite_seq 命中、报告放行，findings 的 file:lines 证据实为未观察内容。应有行为：仅当 read 真正返回了文件行内容时入库。上游防线为何不成立：build_report:567-579 的 cite_seq 校验依赖 EvidenceStore 的诚实性，observe_exact 是其唯一喂入点，此污染直接使校验形同虚设（对空回显 read）。触发条件：模型 read 二进制/越界路径后将其作为 evidence 提交。（src/harness.rs:420-442）
2. 【P1·空 answer 降级报告】harness.rs:212 prose 降级路径取 resp.text.unwrap_or_default() 后仅过 missing_markers（无 required 时恒过），直接构造 Report::degraded_prose 并返回，不调用 validate（validate 的 answer 空检查在 report.rs:67-72 存在但降级路径未走；submit 路径在 build_report:601-603 有显式空检查）。触发条件：模型某轮无 tool_calls 且 text=None（部分网关/tool-call 轮次的 content 为 null），第二轮同形。错误行为：产出 answer=""、confidence=low、degraded=true 的 RunOutcome 以 Ok 返回，渲染出空结论报告，与 submit 路径「answer 为空」打回的承诺（build_report:601）不一致。应有行为：降级路径同样拒空并引导重答。上游防线为何不成立：cli.rs 直接消费 outcome.answer 落盘/打印，对空 answer 无任何检查。（src/harness.rs:212-253、src/harness.rs:601-603、src/report.rs:46-74）
3. 【P1·契约修复预算跨通道共享】harness.rs:112 contract_repaired 是整个 run 会话的单布尔。prose 降级通道在 216-219 消耗一次（contract_steer + degraded_path:true），submit 通道在 288-291 也消耗同一布尔。文档（70-71 行）与 schema 承诺「缺失则补一轮修复引导，仍缺失判 CS2005」——语义应为每个收敛通道各有一轮修复。触发条件：无 required 标记时模型先走一轮 prose（消耗预算）再转 submit 且首轮缺标记。错误行为：submit 首次违约未经自身修复轮直接 CS2005 失败。应有行为：按通道独立预算（或至少 submit 通道保底一轮）。上游防线为何不成立：fuse/契约均无重试，cli.rs:419 直接以 `?` 上抛退出。（src/harness.rs:112-235、src/harness.rs:285-306、src/harness.rs:70-71）
4. 【P2·recall 不计熔断 → 无限空转豁免】对比普通工具：零增量执行在 449-452 明确 no_progress += 1（注释「零增量执行也是无进展步」）。但 recall 分支（337-362）只在有新信息键时重置计数（355-358），无增益时既不重置也不递增——recall 是唯一不推进 no_progress 的执行路径。触发条件：坏模型循环 recall 递增窗口（from=n, to=n+50），每轮产生不同 audit 行文本（seq 前缀不同 → sha256 内容键不同）→ seen_keys 持续新增 → no_progress 持续被清零，可无限循环烧 token 永不触 MAX_NO_PROGRESS_STREAK。错误行为 vs 应有行为：recall 无增益应同样计入 no_progress（或至少不给 reset 豁免）。上游防线为何不成立：llm.rs 无成本上限，唯一防线就是熔断。（src/harness.rs:337-362、src/harness.rs:449-452）
5. 【P2·recall 缺省参数语义陷阱】harness.rs:344-345：from 缺省 0、to 缺省 = from。schema（514）声明 from/to 均 required，但模型漏传 to 时得到 [from,from] 单行或空范围，静默返回「该范围无审计行」，无任何参数错误提示，模型可能在盲区打转（且该空转如上不进熔断计数）。边界代入：from>to 时 read_range 返回空，同样静默。（src/harness.rs:344-346、src/harness.rs:512-514）
6. 【P3·熔断路径审计留痕可能丢失】harness.rs:269/327/369 等处 `if let Some(fuse) = fuse_if_hit(no_progress, &self.audit)?`——fuse_if_hit 内 audit.record 失败时返回 Err(record错误) 而非熔断错误，真实熔断原因被 IO 错误掩盖。轻微（审计写盘失败本身即故障），但与「熔断必留痕」的 P004 T4 意图有偏差。另注：audit.rs:79-92 轮转后 seq 从 1 重开且 append_line 重扫文件取 max——轮转边界多进程追加有混淆窗口，但当前单会话单写者设计下不可达。（src/harness.rs:269-271、src/audit.rs:79-92）
7. 【P3·read.rs 冗余/无害边界】read.rs:133 take(end - offset + 1) 与 skip(offset-1) 双重限制（end 已被 min(total) 封顶），数学上恒 ≥ 实际行数，无害但冗余；offset=0 被 max(1) 归一（79 行），1-based 语义自洽。此文件经边界代入（空文件/越界/二进制/0/1/2000）核对后干净。（src/tools/read.rs:114-135）
8. 【死代码·确定死】CsError::retryable()（errors.rs:93-96）：全仓库 grep 零生产调用（唯一引用是 errors.rs:146 测试），生产一律用 with_retryable(bool)。建议直接删除。（src/errors.rs:93-101）
9. 【死代码·疑似死】McpClient::list_tools（mcp.rs:116-126）：公共 API，生产代码零调用（codegraph 工具集在 cli.rs:324-328 静态注册，从不向 server 查询 tools/list）。可能作为 MCP 生命周期调试/未来能力保留，列排查过程：grep 全仓库仅 docs/contexts 文档提及。（src/mcp.rs:116-126）
10. 【死代码·孤儿簇（预留入口）】RecallEngine::{tombstone, tombstone_count, needs_compact, compact}（recall.rs:68-97）：grep 确认生产零调用，仅测试调用（recall.rs:219/245 及同文件测试）。会话内 RecallEngine 只读不更新，墓碑/压缩机制实为「写一半的功能」——与 audit.rs:166-168 已裁决砍除的账本旁路同类，但这里代码本体仍在。建议标注或按 P004 T5.1 先例裁决。（src/vector/recall.rs:68-97）
11. 【干净面声明】已按三方对质+数据流+边界代入审过且未发现缺陷的段落：① no_progress/zero_gain/prose_streak 三个计数的推进与重置路径（196-262, 264-481），与 harness.rs:1186-1212 的回归测试语义一致；② strip_task_echo 的剥除边界（686-726，有专属测试 858-883 覆盖误剥/多重回显）；③ compact 的 tool-pair 边界回退（context.rs:66-71，有回归测试 163-195）；④ fence 的双层防逃逸（fence.rs:30-55，symlink/绝对路径/不存在三态测试覆盖）；⑤ audit.record 锁内取号写入（audit.rs:144-147）；⑥ mcp request 的 id 匹配与通知忽略（mcp.rs:152-190）。first_user_suffix 追加依赖 last_mut 的 User 匹配（harness.rs:101-106），当前构造恒成立但属脆弱前提，仅记观察不判缺陷。（src/harness.rs:100-106、src/context.rs:62-81）
