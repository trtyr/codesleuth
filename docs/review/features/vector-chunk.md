# 微观 · 向量切块（vector-chunk）

> 置信度 high · 7 条发现 · 384403 tokens

向量切块链路（plan_chunks → build_vector_index → compose_input/embed → VectorStore.commit_build → RecallEngine → CLI/vector_search）整体结构清晰、关键事务与增量复用设计正确（commit_build 原子事务、stale_index 三因子作废、embed 响应 index 对齐校验都对）。发现的真实缺陷集中在「层3兜底与 leftover 无尺寸上限」这一主线上：主块有 MAX_CHUNK_CHARS 限制、超大符号有 SUB_WINDOW_LINES 滑窗，但 leftover 块与 fallback（markdown 节 / 纯文本滑窗）完全不按 MAX_CHUNK_CHARS 再切，最大可达 MAX_FILE_BYTES=400k 字符的单块，违反切块契约并可能在嵌入网关侧失败或质量塌陷——这是最值得先修的。其余为文档漂移（并发数、HNSW 阈值两处注释与代码不符）、build.rs 对 codegraph.db 缺失静默降级为零日志的全文 text 切块，以及 recall 超采候选可能全落墓碑导致 top-K 截断。死代码维度：descriptions 表及其 GC 路径是描述层移除后的有意保留残余（mod.rs 注释自证），无确定死函数。

1. P2 · leftover 与 fallback 块无 MAX_CHUNK_CHARS 尺寸上限：主块走 full.len() <= MAX_CHUNK_CHARS 分支（chunk.rs:310）、超大符号走 sub_window_chunks 滑窗（chunk.rs:322-334），但 leftover 缺口块（chunk.rs:363-379）与兜底的 markdown 标题节（chunk.rs:450-466）/ 纯文本窗口（chunk.rs:435-443）产出后直接 make_chunk，不做任何长度复检。触发条件：一个 >6000 字符的未覆盖区段（如超长常量表、大 markdown 章节）。错误行为：单块最大可达 MAX_FILE_BYTES=400_000 字符（read_lines 只按文件级上限过滤，chunk.rs:49,168-175），违反「块字符上限（≈1500 token）」契约（chunk.rs:13-14），嵌入请求可能被网关按 token 上限拒绝（整个 build 失败）或向量质量塌陷。应有行为：leftover/fallback 产出后按 FALLBACK_WINDOW_LINES 或字符上限二次切分。上游防线不成立论证：embed.rs 无文本长度校验（embed_one 直接把 batch 原文发 /embeddings，embed.rs:149-155），store/commit 也不校验——链路上没有任何一层兜住尺寸。（src/vector/chunk.rs:363-380、src/vector/chunk.rs:434-467、src/vector/chunk.rs:48-49）
2. P3 · build_vector_index 对 codegraph.db 读取失败静默吞掉：symbols_from_codegraph(...).unwrap_or_default()（build.rs:35）失败时 nodes 为空，plan_chunks 走纯 fallback 把整个仓库按 100 行 text 窗口切块——符号边界真源完全失效，且无任何 tracing::warn 留痕。对比同函数内其他降级点（cli.rs:637 构建失败有 warn+audit），此处是零信号的静默质量降级。应有行为：至少 warn 一次说明退化为文本窗口切块。（src/vector/build.rs:34-36、src/vector/chunk.rs:137-165）

P3 · 注释与代码漂移两处：① embed.rs:15 注释说「并发 3 约 1/3」而 :16 EMBED_CONCURRENCY = 4（且注释里「串行 141 批 ~10 分钟」的口径也停在旧值）；② recall.rs:4 模块文档说「<1000 向量走暴力」而 :20 MIN_HNSW_SIZE = 100_000（注释自述 2026-10-05 改为 10 万，模块头注释未同步）。纯文档债，但后者直接误导读者对 HNSW 触发规模的判断。（src/vector/embed.rs:15-16、src/vector/recall.rs:3-4、src/vector/recall.rs:19-20）
4. P3 · recall_by_vector HNSW 路径在墓碑密集时 top-K 截断：knbn = k*3 个候选先查 HNSW 再 filter alive（recall.rs:102-110），若候选大量落在墓碑行，过滤后可能不足 k 条，即使 alive 集里还有合格向量也不回补；compact 阈值 20%（recall.rs:22）意味着墓碑占比 0~20% 区间内欠召回是常态。暴力路径无此问题。疑似→实锤路径明确（代码无回补逻辑），严重度低（会话内影子图场景）。（src/vector/recall.rs:100-114、src/vector/recall.rs:21-22）
5. P3 · 陈旧 codegraph 节点被钳位掩盖成退化 1 行块：start/end 对 lines.len() 做 min/max 钳位（chunk.rs:285-286），当符号行号完全超出当前文件（索引陈旧）时得到 (len,len) 或 (start,start) 的 1 行垃圾块并计入 covered，而不是跳过该符号。symbols_from_codegraph 读库时也不带任何时间戳/一致性校验（chunk.rs:137-165）。触发条件：codegraph.db 与磁盘文件不同步时增量建索引。（src/vector/chunk.rs:285-290、src/vector/chunk.rs:157-158）
6. 死代码维 · descriptions 表及配套 GC 是描述层移除后的残余物：表结构（store.rs:71-75）、GC 删除（store.rs:134-135）、mod.rs 注释自证「store 留 descriptions 表为兼容」（mod.rs:4-5）——当前全链路无任何写入 descriptions 的代码（build.rs 已无描述生成），该表只进不出只删不写，属于有意保留的兼容残余；建议连带 remove_stale_on 里的 descriptions 删除一并评估清理。其余符号核查：upsert_chunk/remove_stale 的非事务包装仅测试引用但为 pub API（不可判死）；hash_of、index_path、project_index_dir、relations_for_symbol 均有生产调用，无确定死代码。（src/vector/store.rs:70-75、src/vector/store.rs:134-135、src/vector/mod.rs:4-5）
7. 已审且未见缺陷的高风险交叉点（说明审法）：① commit_build 事务（store.rs:201-232）与 build.rs 编排——GC 键先算后删、网络调用在事务外、meta 三写同事务，数据一致性正确；② embed 去重回填（embed.rs:77-145）——槽位映射、按批序还原、错误短路均正确，并发 Semaphore 用法正确；③ 增量复用判据 build.rs:63 以 stale_index 三因子（model/dim/mode）+text_hash 复合判定，无「嵌入输入变了仍复用」窗口（mode 变更会触发全量作废）；④ 容器包含关系的 retain/push 算法（chunk.rs:287-302）与滑窗行号换算（chunk.rs:322-334：eff_start+i / eff_start+e-1，边界代入 0/1/len 均正确）；⑤ leftover 区间合并与缺口扫描（chunk.rs:343-362）边界代入无越界；⑥ chunk_key 唯一性与 upsert ON CONFLICT 键一致（store.rs:14-16,179）。（src/vector/store.rs:201-232、src/vector/build.rs:59-83、src/vector/embed.rs:206-220）
