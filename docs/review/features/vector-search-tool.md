# 微观 · vector_search工具（vector-search-tool）

> 置信度 medium · 6 条发现 · 694613 tokens

vector_search 链路整体质量较高（参数校验、k 钳制、全行维度校验、索引对齐校验、事务化 commit_build 等历史修复到位），但仍有 2 个真实正确性缺陷：① setup_vector_layer 的 OpponentFinished 分支与 run_index_vector 的同名分支复制粘贴改漏——后者在复用前检查索引文件存在性，前者不检查，导致锁被 codegraph 引导等其他持有者占用结束时会话静默打开/新建一个空 vectors.db，注册一个永远返回空的 vector_search 工具并向 .codesleuth 写入垃圾库文件（P2）；② EmbedClient::embed_one 错误分支对网关响应 JSON 做 `&snippet[..200]` 字节切片，切点落在多字节 UTF-8 中间会 panic（P2）。另有墓碑/压缩族 API（tombstone/needs_compact/compact/tombstone_count）、with_batch_size、.retryable() 构建器为生产零引用死代码，descriptions 表只写 schema 从不写入数据（孤儿残留）。bug 密度最高文件：src/cli.rs（向量层装配分支）与 src/vector/embed.rs。最值得先修：setup_vector_layer 补索引存在性检查（对齐 run_index_vector:187-196）。

1. P2 · 复制粘贴改漏/数据一致性：setup_vector_layer 的 BootLockOutcome::OpponentFinished 分支直接打印「复用其产物」并跳过构建，但不像 run_index_vector 那样先检查 index_path(...).exists()。共享引导锁被任何其他持有者（如另一进程的 codegraph 引导，或对手构建了别的 fingerprint 索引）占用结束都会触发该分支；随后 VectorStore::open 会无条件 CREATE TABLE 新建一个空 vectors.db，注册的 vector_search 工具查询空索引、召回注入静默为空，且在目标仓库 .codesleuth/ 下留下空库文件（违背「复用其产物」语义，也制造非必要写入）。触发条件：并发进程持有 boot.lock 期间本进程带 --vector 启动。错误行为：静默空召回+垃圾文件；应有行为：检查产物存在，缺失则增量补建或诚实降级。上游防线不成立：run_index_vector 同分支有 .exists() 守卫（cli.rs:187-196），证明作者知晓该前提，setup_vector_layer 漏带即缺陷。（src/cli.rs:647-662、src/cli.rs:187-196、src/vector/store.rs:47-56）
2. P2 · 边界值代入 panic：EmbedClient::embed_one 非 2xx 分支用 &snippet[..snippet.len().min(200)] 按字节切片；snippet 是网关错误响应的 JSON 序列化文本，若第 200 字节落在多字节 UTF-8（如中文错误信息）字符中间，切片直接 panic（应使用 chars().take 或 floor_char_boundary）。触发条件：嵌入端点返回含中文且长度跨过 200 字节边界的错误体。错误行为：进程 panic；应有行为：结构化 CsError。上游防线不成立：这是错误构造路径本身，无任何外层捕获。（src/vector/embed.rs:166-176）
3. 维B · 确定死代码：RecallEngine 的墓碑/压缩族（tombstone/tombstone_count/needs_compact/compact，recall.rs:69-97）全仓 grep 仅测试调用，零生产引用——RecallEngine 是一次性快照（open 后 rows 只读，GC 发生在下次构建的事务里），会话内不存在行号失效场景；EmbedClient::with_batch_size（embed.rs:66-69）零引用；CsError::retryable() 单参构建器（errors.rs:93-96）仅 errors.rs:146 测试使用。最值得先清理：墓碑族 API（连同 TOMBSTONE_REBUILD_RATIO 常量），或补上真实失效通知链路。（src/vector/recall.rs:68-97、src/vector/embed.rs:66-69、src/errors.rs:93-96）
4. 维B · 孤儿残留：descriptions 表建了 schema 且 remove_stale_on 会 DELETE 它，但全仓无任何 INSERT——描述层功能已于 2026-10-04 裁决移除（vector/mod.rs 注释自认），留下「只删不写」的半截兼容残余。（src/vector/store.rs:71-75、src/vector/store.rs:134-135、src/vector/mod.rs:4-5）
5. P3 · 文档/注释漂移：recall.rs 头注释写「<1000 向量走暴力」，实际常量 MIN_HNSW_SIZE=100_000（注释自述 2026-10-05 拍板改为 10 万，头注释未同步）；同文件三段式描述顺序与实现一致但「<1000」口径已失真，误导后续维护者。（src/vector/recall.rs:3-4、src/vector/recall.rs:19-20）
6. 已审干净部分（说明审法）：VectorSearchTool::execute 的 query 判空、k 经 as_u64+clamp(1,10)（负数/0/超大/浮点/字符串型 k 均安全降级）；RecallEngine::open 的全行维度校验与 model 校验降级、recall 嵌入空向量防御、recall_by_vector HNSW d_id 与 rows 下标一致性（build_hnsw 以行号为 id 插入）、cosine 零向量守卫；embed 的去重回填槽位映射、批序还原、响应条数校验与 0-based 对齐校验（validate_index_alignment）；store 的 commit_build 单事务原子性、remove_stale 幂等计数——逐一以空/零/一/负/最大值代入心算，未发现新缺陷。（src/tools/vector_search.rs:48-63、src/vector/recall.rs:34-52、src/vector/embed.rs:178-203）
