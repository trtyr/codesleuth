# 微观 · 向量存储（vector-store）

> 置信度 medium · 6 条发现 · 275376 tokens

向量存储链路整体质量较高（原子事务、维度全行校验、index 对齐校验等历史修复到位），但仍有真实缺陷：最严重的是 embed.rs 错误分支按字节切片截断错误消息可 panic（UTF-8 多字节切断，P2）；其余为召回降级路径的静默错配（dim 不一致时 cosine zip 截断仍打分，P3）、setup_vector_layer 中 RecallEngine::open 用 `?` 破坏既定降级语义（P3）、embed_one 在状态检查前先解析 JSON 导致非 JSON 错误体丢失状态信息（P3）。死代码维度：tombstone/needs_compact/compact/tombstone_count 为仓库自知的「预留入口」（仅测试调用、有文档登记，不算误杀项但属未接线功能）；EmbedClient::with_batch_size 零调用方（公共 API 不可判死）；remove_stale 包装器生产路径零调用；descriptions 表为已裁决移除的描述层遗留。

1. P2 · embed.rs 错误分支按字节切片错误摘要，可 panic：`&snippet[..snippet.len().min(200)]` 是字节切片，serde_json::Value::to_string() 不转义非 ASCII（保持 UTF-8），若网关错误响应含中文/多字节字符且恰在第 200 字节边界切断多字节字符，将 panic（byte index not a char boundary）。触发条件：非 2xx 响应 + 错误体前 200 字节内含多字节字符且边界未对齐。错误行为：进程 panic；应有行为：返回结构化错误。上游防线不成立：这是错误处理的最外层（构造 CsError 时即 panic），无任何上层兜底。（src/vector/embed.rs:166-177）
2. P3 · 召回降级路径维度错配静默打分：RecallEngine::open 在 model 不符时跳过 HNSW 但仍走暴力路径（recall_by_vector 无 dim 检查），cosine 用 `a.iter().zip(b.iter())` 截断到较短向量——查询 1024 维 vs 库内 4096 维时前 1024 维点积/部分模长得到无意义相似度并正常排序返回，误导 agent。触发条件：换嵌入模型/维度后旧 vectors.db 未清（stale_index 只在 build 时判定，build 失败降级路径 cli.rs:636-644 会直接复用旧库）。已有测试 meta_mismatch_skips_hnsw_but_brute_still_works 把此行为固化，属设计缺陷而非笔误，故降为 P3 疑似。验证方法：构造 model meta 不符 + dim 不符的库，对比暴力召回与重嵌后的排序差异。（src/vector/recall.rs:100-125、src/vector/recall.rs:36-52、src/vector/store.rs:289-301）
3. P3 · setup_vector_layer 降级语义不一致：函数注释与 store 打开失败分支承诺「向量不可用 → Ok(None) 弹性降级不致命」，但第 659 行 `RecallEngine::open(store, embed)?` 直接用 `?` 上抛——load_all 任一 SQLite 行读错（含单行损坏）即让整个任务启动致命失败。上游防线不成立：这是 run_task_inner 的装配点，`?` 之上无针对该错误的降级分支。（src/cli.rs:651-659、src/cli.rs:598-660）
4. P3 · embed_one 先 resp.json() 后判状态：非 2xx 且错误体非 JSON（如 HTML 502 页）时，json 解析先失败，错误消息只剩「响应解析失败: ...」而 HTTP 状态码与 retryable 分类（429/5xx）全部丢失，调用方与外层重试判断失去依据。应有行为：先取 status，非成功分支用 bytes/text 构造带状态码的错误。上游防线不成立：这是该请求的最外层解析，with_retryable 分类在同一路径上，信息在源头即被吞掉。（src/vector/embed.rs:162-165）
5. 审过且干净的段落（说明审法）：①增量复用条件 `!stale_index && existing.get(&key) == Some(&c.text_hash)` 与 compose_input 的确定性（text 决定 header+identifiers）三方对质一致，mode 变更由 stored_meta 捕获，无「复用即投毒」窗口；②commit_build 事务用 unchecked_transaction 包 GC+upsert+meta，失败回滚，与 build.rs「网络调用在事务外」的调用时序一致，无部分提交中间态；③blob_to_vec 用 as_chunks 忽略尾部残字节（4|len 恒成立因 vec_to_blob 按 f32 写），roundtrip 测试覆盖；④chunk_key 的 '\u{1}' 分隔符与 existing_hashes 重组格式逐字对齐；⑤plan_chunks 边界代入（空文件、start/end 钳制、滑窗 SUB_WINDOW_LINES>SUB_OVERLAP_LINES、markdown 首节）均心算验证无越界/死循环；⑥embed 去重回填 slots 与 validate_index_alignment 0-based 对齐校验逻辑核对无误。（src/vector/build.rs:44-67、src/vector/compose.rs:42-51、src/vector/store.rs:201-232）
6. 死代码盘点：确定死（生产路径零引用，但因 pub 不可武断）——EmbedClient::with_batch_size（全仓唯一命中即定义本身，batch_size 恒为 64 构造期硬编码）、VectorStore::remove_stale 包装器（生产走 commit_build/remove_stale_on，仅测试调用）；预留入口（仓库自知）——RecallEngine::tombstone/tombstone_count/needs_compact/compact 仅测试调用，docs/contexts/向量检索/04-vector-recall.md 已登记为「预留入口」；遗留物——descriptions 表与 schema 建表仍在（mod.rs 注明「留为兼容」），其写入路径已不存在，仅 remove_stale_on 单向清删，属永久只写不进的残留。（src/vector/embed.rs:66-69、src/vector/store.rs:105-110、src/vector/recall.rs:69-97）
