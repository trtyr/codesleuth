# 微观 · 结构图工具集（graph-tools）

> 置信度 high · 9 条发现 · 498325 tokens

链路整体设计（bootlock 串行化引导 → spawn MCP → initialize → 五 Tool → Arc<CodegraphEngine>::call 注 projectPath → JSON-RPC stdio → Drop 回收）实现质量较高，未发现 P0/P1 级正确性缺陷。确认的问题集中在 src/mcp.rs：(1) Drop 用 try_lock 回收子进程，锁竞争时静默跳过 start_kill 造成子进程泄漏（P2）；(2) call_tool 的请求级 JSON-RPC error 与响应 isError/空内容全部映射为 INDEX_BUILD_FAILED(CS4011「构建失败」)，与错误码语义三方不一致（P3）；(3) request 的写-读两段锁在多任务并发共享引擎时理论上可丢/串响应（当前单消费者架构下不触发，疑似）。另有两处文档-代码漂移：graph.rs 模块注释宣称 CODEGRAPH_NO_DAEMON=1 独占机制但代码从未设置该 env（docs 已自查确认）；symbol_args 对 callees/impact 也无条件透传 limit/depth，与 Tool description 声称的参数面不符。死代码维度：McpClient::list_tools 为零调用方的 pub 方法（疑似死，可辩护为协议完整性 API）。最值得先修：Drop 的 start_kill 改为 wait锁或忽略结果改为总是 kill。

1. 【P2·并发/生命周期】McpClient::Drop 用 try_lock() 回收子进程：若此刻 child Mutex 被并发请求持有（任一 in-flight request 持 child 锁的场景不存在，但 stdin/reader 锁与 child 锁独立，child 实际只在 Drop 内触碰——更现实的触发是 Drop 与并发 request 竞态或未来重构），try_lock 失败即静默跳过 start_kill，codegraph serve 子进程泄漏为孤儿。应有行为：阻塞等待锁或泄漏时记 warn 日志。上游防线不成立：cli.rs:421 的显式 drop(cg) 也走同一 Drop 路径，无第二道回收。（src/mcp.rs:198-204）
2. 【P3·API 误用/错误语义错位】call_tool 把所有请求级失败统一映射为 INDEX_BUILD_FAILED(CS4011)。三方对质：errors.rs 定义 4011 为「构建失败」段位（exit 5），但 mcp.rs:181-185 把 JSON-RPC error（含 method not found、参数校验失败等工具调用期错误）也标 4011；extract_tool_text 对 isError=true 与「空内容（符号不存在或索引未就绪？）」同样标 4011。工具调用期错误被包装成「构建失败」，错误码承诺与实际语义不一致；上游 harness/agent 按 code 分类重试或提示时会误导。（src/mcp.rs:128-133、src/mcp.rs:38-53、src/errors.rs:47-53）
3. 【疑似 P2·并发正确性，当前架构不触发】request() 的写锁（stdin.lock）与读锁（reader.lock）分两段获取、不原子。单会话单 agent 顺序调用下安全；但 CodegraphEngine 是 Arc 共享、五个 Tool 均持引用，若未来引入并发 execute，两个 request 交错写行后各自循环读，B 可能读到 A 的 id 响应并跳过（id 不匹配则丢弃该行——被跳过的响应正是 B 自己后续要等的那行已被 A 消费丢弃，导致 B 超时）。当前 McpClient 注释明示「顺序请求-响应（单会话单 agent）」契约成立，故列疑似；验证方法：并发 tokio::spawn 两个 call_tool 观察超时。（src/mcp.rs:135-190）
4. 【P3·文档-代码漂移】graph.rs 模块注释宣称「CODEGRAPH_NO_DAEMON=1 保证每会话独占进程」，但代码中无任何 .env("CODEGRAPH_NO_DAEMON") 设置点（仓库 docs/contexts/结构图与MCP/01-graph-tools.md:301 已自查确认同样结论）；实际独占仅靠 Arc 所有权 + Drop start_kill。若 codegraph serve 默认 fork daemon，注释承诺的独占假设不成立。运行期实际只设 CODEGRAPH_TELEMETRY=0 与 DO_NOT_TRACK=1。（src/tools/graph.rs:1-5、src/tools/graph.rs:25-67、src/mcp.rs:68-76）
5. 【P3·三方对质】cg_symbol_tool 宏对 callees（描述声称 args:{symbol}）与 impact（声称 {symbol,depth}）统一暴露 limit+depth schema 且 symbol_args 无条件透传两者；callers 描述含 limit 但 depth 文案写「impact 用」。描述与实际参数面不一致，agent 可能按描述构造被拒或误用；行为无害但属承诺不一致。（src/tools/graph.rs:121-135、src/tools/graph.rs:177-191、src/tools/graph.rs:156-166）
6. 【P3·边界】start_with_bin 的 OpponentFinished 分支与 Won-且非-force-且 .codegraph 存在分支都跳过 init/force；若 .codegraph 目录存在但内部 codegraph.db 缺失/损坏（对手崩溃半途），serve/查询将失败。cli.rs 侧有 graph_symbols_nonempty 复核（repo_map_inputs 打开 db 失败→不注册图工具+地形提示）兜底了工具注册面，故仅降级为提示级问题：force_reindex 时 OpponentFinished 分支也跳过重建，--fresh-index 在锁竞争下静默失效。（src/tools/graph.rs:83-96、src/cli.rs:313-336）
7. 【已审干净项】五工具注册链（cli.rs:322-335 条件注册 + graph_symbols_nonempty 诚实降级 + 地形提示）、CodegraphEngine::call 的 projectPath 注入与 codegraph_ 前缀、FilesTool 空 Map 构造、ExploreTool query 判空、symbol_args USER_INPUT 校验（graph.rs:288-300 测试覆盖）、ToolRegistry::get 按 name 查表（mod.rs:38-43 线性 find 无重名冲突）、cli.rs:421 显式 drop(cg) 时序（agent 先 drop 再 drop cg）均逐一读穿核对，无逻辑/边界错误。（src/cli.rs:292-336、src/cli.rs:419-421、src/tools/graph.rs:75-110）
8. 【疑似死代码】McpClient::list_tools 零调用方（codegraph callers 确认 No callers；grep 仅命中定义与文档），是初始化握手后从未使用的 pub 方法——protocol 完整性 API 可辩护，建议要么在握手后校验五工具存在（真正用起来），要么删除。（src/mcp.rs:116-126、src/mcp.rs:105-114）
9. 【bootlock 交叉点已核】graph 引导与向量构建共用一把锁（cli.rs:182 与 graph.rs:78 同一 .codesleuth/boot.lock），acquire 的轮询路径拿到即 drop(file) 放锁再返回 Lost，无双重持锁；300s 超时与 run_cli 的 300s 对齐。无缺陷。（src/bootlock.rs:101-121）
